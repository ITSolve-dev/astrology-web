# Тестирование

**Стек:** Vitest · Playwright · @vitest/coverage-istanbul

---

## 1. Что и как тестируем

### Приоритет уровней

```
Integration (Vitest)   ←  основной слой: логика и слой сети
E2E (Playwright)       ←  ключевые пользовательские сценарии через UI
Unit (Vitest)          ←  только переиспользуемые чистые утилиты
```

Нет stage-окружения — тесты единственная защита перед продакшеном.

Интеграционные тесты запускаются против реального бэкенда в контейнере. E2E через Playwright — единственное место где проверяется то, что видит пользователь.

### Что тестируем

- Слой взаимодействия с сервером: корректность запросов, обработка ответов и ошибок (integration)
- Логику стора: трансформации данных, переходы состояний (integration)
- Критические пользовательские сценарии от начала до конца через браузер (e2e)
- Переиспользуемые чистые утилиты: парсеры, форматтеры, конвертеры (unit)

### Что не тестируем

- UI-рендеринг на уровне интеграционных тестов — это зона E2E
- Детали реализации: имена функций, внутреннюю структуру модулей
- Приватные методы и внутренние хелперы — покрываются транзитивно
- Стили и классы

### Тест считается валидным, если

- Падает при регрессии в поведении
- Не падает при рефакторинге внутренней реализации
- Воспроизводим и детерминирован при любом порядке запуска

## 2. Структура теста: Given — When — Then

Каждый тест явно делится на три части. В одном тесте — ровно одно When.

```ts
it('возвращает данные профиля при успешном ответе сервера', async () => {
  // Given
  const profile = await api.createProfile({ name: 'Test User' })
  // When
  const result = await fetchProfile(profile.id)
  // Then
  expect(result.name).toBe('Test User')
})
```

## 3. Уровни тестирования

### Integration (Vitest) — основной слой

**Когда:** нужно проверить логику взаимодействия с сервером, обработку ответов или логику стора.

**Окружение.** Тесты запускаются против реального бэкенда в контейнере с пустой БД. Тестовые данные создаются внутри теста через публичный API бэкенда. Конфигурация контейнера — в `docker-compose.test.yml` (ответственность бэкенд-команды).

> **Открытые вопросы (нужно синхронизироваться с тимлидом):**
> - Как поднимается контейнер с бэкендом локально и в CI
> - Есть ли endpoint или скрипт для сброса БД между прогонами
> - Кто отвечает за `docker-compose.test.yml`

**Что проверяем:**
- API-клиент: корректность запросов, обработка успешных ответов и ошибок
- Логику стора: трансформации данных, обработка мутаций
- Публичные функции и модули, которыми пользуется остальное приложение
- Граничные состояния: пустой ответ, сетевая ошибка, 500

**Правила:**
- Тестируем через публичный API модуля
- Никаких `vi.mock` на внутренние модули
- Изоляция стора в `beforeEach(() => store.reset())`
- Каждый тест стартует на чистом состоянии

**Минимум тестов на сценарий:**

| Сценарий | Минимум | Почему |
|----------|---------|--------|
| GET-запрос / fetch-функция | 3 | success, пустой ответ, 500 |
| Мутация (POST/PUT/DELETE) | 3 | success, server error, validation error |
| Обработчик ошибок | по одному на тип | каждый тип — отдельная ветка |
| Трансформация данных в сторе | по одному на ветку | каждое условие — отдельный тест |

**Пример — тест слоя сети:**

```ts
// features/profile/__tests__/loadProfile.test.ts
describe('loadProfile', () => {
  describe('успешный ответ', () => {
    it('возвращает данные профиля', async () => {
      // Given
      await api.createProfile(createProfile({ name: 'Test User' }))
      // When
      const result = await fetchProfile()
      // Then
      expect(result.name).toBe('Test User')
    })
  })

  describe('граничные состояния', () => {
    it('возвращает пустой массив если профилей нет', async () => {
      // Given — БД чистая
      // When
      const result = await fetchProfiles()
      // Then
      expect(result).toEqual([])
    })
  })
})
```

### E2E (Playwright) — пользовательские сценарии

**Когда:** сценарий критичен и требует проверки через реальный браузер.

**Что покрываем:**
- Auth-флоу: вход → редирект на главный экран
- 2–3 ключевых бизнес-сценария
- Сценарии где недостаточно интеграционного теста: редиректы, межфичевые флоу

**Правила:**
- Локаторы только через `getByRole`, `getByLabel`, `getByText` — `locator('.classname')` запрещён
- `page.waitForTimeout()` запрещён — только `waitForSelector`, `waitForResponse`, `expect(locator).toBeVisible()`
- Каждый тест изолирован, без зависимости от других тестов

```ts
// e2e/auth.spec.ts
test('успешный вход редиректит на /app/home', async ({ page }) => {
  // Given
  await page.goto('/')
  // When
  await page.getByLabel('Телефон').fill('+7 999 000 00 00')
  await page.getByRole('button', { name: 'Войти' }).click()
  // Then
  await expect(page).toHaveURL('/app/home', { timeout: 5000 })
})
```

---

### Unit (Vitest) — только чистые утилиты

**Когда:** переиспользуемая чистая функция без зависимостей от React, DOM и сети.

**Правила:**
- Параметризация обязательна — `it.each()`, не серия одинаковых `it()`

```ts
describe('parseApiError', () => {
  it.each([
    [new ApiError('Не авторизован'), 'Не авторизован'],
    [new NetworkError(),             'Нет соединения'],
    [new Error('unknown'),           'Что-то пошло не так'],
  ])('возвращает корректное сообщение для %s', (error, expected) => {
    expect(parseApiError(error)).toBe(expected)
  })
})
```

## 4. Изоляция зависимостей

```
Свой код фронтенда       →  реальная реализация (обязательно)
HTTP-запросы к бэкенду   →  реальный бэкенд в контейнере (обязательно)
Внешние third-party      →  fake-реализация контракта
```

Внутренние модули не мокируются никогда.

## 5. Тестовые данные

Источник данных — только фабрики. Никаких инлайн-объектов в тестах.

```
tests/
└── factories/
    ├── profile.ts    # createProfile(overrides?)
    ├── user.ts       # createUser(overrides?)
    └── index.ts
```

```ts
export function createProfile(overrides?: Partial<Profile>): Profile {
  return {
    id: 1,
    name: 'Test User',
    avatarUrl: 'https://example.com/avatar.png',
    ...overrides,
  }
}
```

**Правила:**
- Данные всегда детерминированы — никакого `Math.random()` или `Date.now()`
- Фабрики принимают `overrides` для тест-специфичных значений
- Фикстуры создаются внутри теста, не глобальным seed'ом

## 6. Структура файлов и именование

```
features/
└── profile/
    ├── __tests__/
    │   ├── loadProfile.test.ts
    │   ├── updateProfile.test.ts
    │   └── parseProfileData.test.ts
    └── ...
tests/
├── factories/
└── fakes/
e2e/
├── auth.spec.ts
└── criticalFlow.spec.ts
```

| Уровень | Шаблон | Пример |
|---------|--------|--------|
| Integration | `<сценарий>.test.ts` | `loadProfile.test.ts` |
| Unit | `<утилита>.test.ts` | `parseApiError.test.ts` |
| E2E | `<флоу>.spec.ts` | `auth.spec.ts` |

Именование тестов — `[сценарий] [действие] [ожидаемый результат]`:

```ts
// ✅ Правильно
it('loadProfile возвращает данные при успешном ответе сервера')
it('parseApiError возвращает fallback для неизвестных ошибок')

// ❌ Неправильно
it('works correctly')
it('fetchProfile работает')
```

## 7. Запуск тестов

```bash
make test
```

| Ситуация | Что запускать |
|----------|---------------|
| PR / полная проверка | Полный набор |
| Перед деплоем | Critical/smoke набор |
| Отладка одного теста | Один файл или тест по имени |
| AI-агент написал тест | Изолированный запуск одного файла |

---

## 8. CI

На каждый PR — полный набор тестов. Красный CI блокирует merge.

Артефакты каждого прогона: отчёт покрытия (`@vitest/coverage-istanbul`), логи упавших тестов.

Critical-набор отмечается тегом `@critical`. Критерий: поломка напрямую влияет на пользователя или выручку.

## 9. Антипаттерны

| Антипаттерн | Что делать вместо |
|-------------|-------------------|
| `vi.mock('@/features/auth/model/store')` | Реальный стор + реальный бэкенд |
| `store.getState()` как assertion | Проверять возвращаемое значение публичной функции |
| `await new Promise(r => setTimeout(r, 500))` | `await` промиса |
| Инлайн-объекты без API-запроса | Фабрики + создание через реальный API |
| `expect(fetch).toHaveBeenCalled()` | Проверять результат — возвращаемые данные |
| Один тест проверяет success и error | Разбить на отдельные тесты |
| Серия одинаковых `it()` | `it.each()` с таблицей кейсов |
| Имя файла по слою: `profileApi.test.ts` | По сценарию: `loadProfile.test.ts` |

## 10. Чеклист для AI-агента

- [ ] Определён уровень: integration / e2e / unit
- [ ] Тест обращается к публичному API модуля, не к внутренностям
- [ ] Никаких `vi.mock` на внутренние модули
- [ ] Тестовые данные создаются через реальный API-запрос, не инлайн
- [ ] Unit-тест использует `it.each()`, не серию отдельных `it()`
- [ ] Структура: Given — When — Then, одно When
- [ ] Имя файла и теста описывают сценарий, не слой
- [ ] Тест проходит изолированно, не зависит от других тестов
- [ ] Стор сбрасывается в `beforeEach`
